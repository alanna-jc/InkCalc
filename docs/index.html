InkCalc: An Offline Embedded Handwriting Recognition Calculator

InkCalc turns handwriting into mathematics. Write an expression on a touchscreen with a stylus — a CTC-Transformer reads the pen strokes, converts them to LaTeX, and a symbolic solver evaluates the result. Everything runs offline on a Raspberry Pi 4.

Capability

What it can solve

Once an expression is recognised, a SymPy-based solver interprets the LaTeX and computes an answer. The recogniser's 255-token vocabulary covers the full symbol set below.

＋

Arithmetic

Numeric evaluation including fractions, powers and roots — 2+4, \frac{10}{2}, 2^{10}, \sqrt{16}.

𝑥

Symbolic algebra

Simplification of expressions containing variables, e.g. x²+2x+x² collapsed to its factored form.

＝

Equation solving

Single- and multi-variable equations — x²+5x+6=0 returns x = −2, −3.

▦

Matrices

Display, multiplication and equality checks, plus linear systems Ax = b with unique, infinite or inconsistent outcomes.

∑

Big operators

Summations, products and definite or indefinite integrals — ∑ᵢ₌₁ⁿ i → n(n+1)/2.

⚒

Structural repair

Recovers from common recogniser slips before solving: unbalanced braces, doubled sub/superscript markers and ragged matrix rows.

Known limits. Transcendental functions (sin, cos, log, exp) and limits (\lim) are absent from the training vocabulary, so they cannot yet be recognised. Supporting them requires both new vocabulary tokens and a solver-side normalisation layer.

Architecture

How it works

Three stages, all executing locally on the Pi. The recogniser is the machine-learning component; the solver and interface are deterministic software around it.

STAGE 01

Recognition

Pen strokes are converted into a sequence of [dx, dy, dt, pen] feature vectors, then a Transformer encoder with a CTC head emits a LaTeX token sequence.

STAGE 02

Solving

SymPy parses the LaTeX and computes a result — arithmetic, symbolic simplification, equation solving or matrix operations, depending on what was written.

STAGE 03

Interface

A pygame touchscreen application captures ink, displays the recognised expression for confirmation, and renders the final answer.

Data

From ink to tensors

Handwriting arrives as an online signal — a time-ordered trajectory, not a picture. Preprocessing turns that raw trajectory into a fixed-format numeric sequence the network can consume, and the identical transform runs on the Pi at inference time so that training and deployment never diverge.

Why deltas, not coordinates

Encoding each point as a displacement from the previous one makes the representation translation-invariant: the same symbol written in a different part of the screen produces the same feature sequence.

Why resample by distance

Touchscreens sample at different rates, so raw point density reflects hardware and writing speed rather than shape. Resampling at a constant spatial step of 0.05 normalised units makes geometry consistent across devices and writers.

Why keep Δt

Resampling deliberately discards temporal density, so elapsed time is preserved explicitly as a third channel — letting the model distinguish a slow, deliberate stroke from a fast one.

Why a pen-state flag

A flattened point sequence loses stroke boundaries. A binary channel marking the final point of each stroke restores them, which matters for multi-stroke symbols such as = and ÷.

Network

The recogniser

An encoder-only Transformer with a Connectionist Temporal Classification head, replicating the CTC baseline of the MathWriting paper. CTC removes the need for point-level alignment labels: the network learns for itself which timesteps correspond to which symbols.

  • Embedding dimension512
  • Attention heads8

  • Dropout0.15
  • Positional encodingsinusoidal, fixed

Design notes

  • Encoder-only. CTC needs one output per input timestep, not autoregressive generation, so no decoder stack is required — which also keeps inference cheap enough for a Pi.
  • Fixed positional encoding. Self-attention is permutation-invariant; sinusoidal encodings inject stroke order without adding trainable parameters.
  • Padding masks throughout. Batches contain sequences of differing length, and the mask prevents attention from ever reading padded positions.
  • 512-point ceiling. Analysis of the training samples found their lengths sat well under 512 points, so it was a safe cap — roomy enough for effectively every expression while keeping the quadratic attention cost bounded.
Training

Fifty epochs

Trained on the full MathWriting-2024 human-written split. Validation character error rate falls sharply for the first ten epochs, then grinds down steadily to a best of 5.34%; the fully held-out test set measures 6.67%. Validation loss reaches its minimum at epoch 16 and rises afterwards while CER keeps improving — the model is becoming more confident on the cases it gets right, which inflates likelihood-based loss without harming decoded accuracy. Checkpoints are therefore selected on CER, the metric that matches deployment.

Engineering notes

  • Single-GPU by design. The whole run fits on one 8 GB consumer card as a single process — no gradient synchronisation or multi-GPU launch orchestration to manage, trading wall-clock time for a far simpler pipeline.
  • Batch/learning-rate scaling. Constrained GPU memory forced smaller batches, so the learning rate was scaled down alongside it to keep the two in balance.
  • Mixed precision. Half-precision arithmetic with loss scaling cut memory enough for the pipeline to train on a single 8 GB consumer card, with the scheduler advanced only on steps the scaler actually applied.
  • Staged validation. A three-stage smoke test — gradient flow, padding-mask invariance and positional-encoding sensitivity — ran before every long job, catching wiring faults in seconds rather than GPU-days.
Evaluation

Where it succeeds, where it slips

On 7,644 held-out test expressions the model reproduces 54.3% (4154/7644) exactly, token for token — a demanding bar, since a single misread brace fails the whole expression. The failures that remain are overwhelmingly small: 42% of mismatches differ by a single token and 78% by three or fewer.

Deployment

Getting it onto the Pi

The training environment never ships. The checkpoint is converted to a self-contained ONNX graph so that inference on-device needs only onnxruntime and NumPy — no PyTorch on a machine with 4 GB of RAM.

Self-contained graph

The exported model takes ink points and a padding mask, and applies the log-softmax inside the graph, so the runtime needs no post-processing library.

Verified parity

A parity check confirms the ONNX export and the original checkpoint produce matching outputs before anything is copied to the device.

Shared preprocessing

On-device feature extraction mirrors the training transform exactly — same normalisation, same resampling step, same 512-point ceiling — so there is no train/serve skew.
